## 01. Begin with the decision, not the diagram

An AI architecture is often introduced as a box labelled “model” surrounded by
boxes labelled “data” and “API.” That picture is easy to draw and difficult to
operate. A model is only one component in a chain that collects or receives
signals, validates them, selects a version, computes an output, communicates
uncertainty, supports a user or another system, and records evidence for later
review. The chain also has people: someone defines an acceptable error, someone
owns a data source, someone responds when a service degrades, and someone has
authority to stop a deployment. Architecture is the set of boundaries and
decisions that lets all of those responsibilities remain understandable as the
system changes.

Consider a document-triage product for a support organisation. Its desired
outcome is not “run a transformer.” A useful outcome might be that an incoming
document is assigned to a queue, with a reason and an abstention path, within a
declared time budget. That outcome requires an input contract, malware and
privacy checks, text extraction, a feature or embedding transformation, model
selection, an output policy, human review, storage retention, and monitoring for
drift. A fast prediction with an untraceable source document can be worse than a
slower prediction that a reviewer can audit. Architecture therefore begins with
the decision the system supports and the harms it must avoid.

The official topic list for this subject includes end-to-end design, components,
architectural styles, agentic architecture, ADLC, gateways and protocols,
system-level principles, scalability, performance, resiliency, domain
blueprints, infrastructure integration, production, and governance. Those topics
are not independent chapters in a real service. A scalability decision changes
the failure modes; an agent gateway changes the trust boundary; a governance
requirement changes what may be logged. This chapter follows one running case so
that each concept has a place in an evolving design.

Start with a one-page decision statement. Name the users and affected parties,
the action supported by the output, the latency and availability target, the
data classes involved, the escalation path, and the evidence needed to defend a
decision. Do not promise a metric until its measurement population is defined.
“Ninety-nine percent accurate” is incomplete without a dataset, label policy,
time window, subgroup analysis, and a statement of what happens when the model
is unsure. An architecture review that cannot state those boundaries is a
technology tour, not a design review.

## 02. Draw a map from signal to accountable outcome

The first useful map follows a request or event, not a Kubernetes cluster. A
client submits a document and context. An ingress boundary authenticates the
caller and applies size and rate limits. A validation component checks schema,
encoding, and policy. A preprocessing step extracts permitted features. A model
service loads a pinned artefact and emits a score, label, or abstention. A
decision policy maps that output to an action. A human or downstream workflow
accepts, corrects, or rejects the suggestion. Telemetry records timing, model
version, policy version, and non-sensitive identifiers. A governance store keeps
the evidence needed to reproduce the decision under an approved retention rule.

Write each box as a responsibility with an owner, input contract, output
contract, failure modes, and data classification. “Feature store” is not a
responsibility until it says which features it serves, how freshness is measured,
and what happens when a value is unavailable. “Monitoring” is not a plan until
it says which signal triggers an alert, who receives it, and which runbook limits
the harm. Explicit ownership prevents the familiar condition in which a model
team owns accuracy, a platform team owns uptime, and nobody owns the effect of a
schema change on either one.

The running case has six boundaries:

1. **Interaction:** a web client or queue submits a document reference, tenant,
   and declared purpose; raw content is not echoed in telemetry.
2. **Intake:** authentication, authorization, malware scanning, size limits, and
   idempotency protect the entry point.
3. **AI decision:** extraction, model inference, calibration, and abstention are
   versioned together enough to explain the output.
4. **Action:** a policy service sends a recommendation to a queue while a human
   remains able to correct it.
5. **Infrastructure:** compute, storage, queues, secrets, and network policy
   provide a replaceable operating substrate.
6. **Governance:** evaluation, approvals, audit records, incident response, and
   deletion requests constrain the whole path.

This map also clarifies where an agentic system would fit. An agent is not an
unbounded replacement for every service. It is a component that selects or
composes actions under a goal, often using a language model and tools. The tool
gateway must authenticate the agent, constrain arguments, enforce authorization,
and return typed results. If a planning loop can call a document deletion tool,
that capability belongs on a different trust boundary from a read-only search.

## 03. Turn components into contracts and styles

Use a contract tuple as a compact reasoning aid:

$$
\mathcal{A}=(D,M,P,I,O,G),
$$

where $D$ is data and feature provenance, $M$ is the model and evaluation
artefact, $P$ is the product policy, $I$ is infrastructure, $O$ is observable
operation, and $G$ is governance. This is not an industry standard notation;
it is a checklist for architectural completeness. A design that names $M$ but
not $P$ has no answer for thresholds or abstention. One that names $I$ but not
$D$ cannot explain whether training and serving features mean the same thing.

Four styles are useful comparison points. A **modular monolith** keeps intake,
policy, and inference in one deployable process with internal modules. It is
often the simplest way to preserve a transaction and debug a change. A
**service-oriented** style splits responsibilities where independent ownership,
scaling, or isolation justifies a network boundary. It adds serialization,
versioning, and partial failure. An **event-driven** style moves work through
durable events and queues, which supports smoothing and replay but introduces
ordering, duplication, and eventual consistency. An **agentic composition** adds
goal-directed planning and tool calls; it can support open-ended workflows but
requires stronger policy, sandboxing, budgets, and evaluation than a fixed
pipeline.

Choose a style with evidence. Ask whether a boundary needs independent scaling,
different data access, a separate release cadence, or a distinct blast radius.
If not, a network split may be architecture theatre. Ask whether the user needs
an immediate answer or whether a queue and human review are acceptable. Ask how
the team will test a failure in each dependency. A diagram with fifteen services
is not mature if its owners cannot explain timeout, retry, schema compatibility,
and rollback for each arrow.

The same endpoint can be represented as a function for a first test:

$$
\hat{y}=f_{\theta,v}(x),
$$

where $x$ is a validated input, $\theta$ is the model artefact, and $v$ is the
preprocessing and policy version. In production, the observable result should
carry a stable model-and-policy identifier, a request or event identifier, and
an uncertainty or abstention state where applicable. Returning only a label
removes the context needed to distinguish a model change from a data change.

## 04. Walk through ADLC as an evidence trail

The AI Development Life Cycle (ADLC) links a product question to an operated
system. The exact process varies by organisation, so the stages below are a
proposed teaching interpretation of the official ADLC topic, not a claim about a
particular university template.

First frame the problem and harm: who benefits, who may be disadvantaged, what
decision is being assisted, and what must never be automated. Then inventory and
govern data: provenance, consent or lawful basis, licensing, retention,
redaction, label quality, and representative coverage. Next establish a baseline
that can be reproduced before trying a larger model. Define evaluation slices
and operational metrics before tuning; otherwise a convenient aggregate can hide
failure where the system is actually used.

Training creates more than weights. It creates code, dependency locks, data
manifests, feature definitions, random seeds, and an evaluation report. Package
those artefacts with a model card or equivalent decision record. Validation then
checks both predictive behaviour and contract behaviour: malformed inputs,
missing features, stale data, latency, memory, authorization, and safe
abstention. Deployment is a controlled change with an owner, rollback path,
monitoring window, and explicit stop conditions.

Operation closes the loop. Monitor input schema and freshness, output
distributions, human corrections, resource use, latency percentiles, error
rates, and subgroup or domain slices where permitted. A drift alarm is a prompt
to investigate, not proof that a model is unfair or obsolete. Retire data,
models, credentials, and infrastructure according to a documented policy. A
retraining trigger should not silently promote a new model; promotion remains a
reviewed decision.

The evidence trail can be modelled as a directed graph: a release node points to
the data manifest, code commit, evaluation run, approvals, and deployed image.
If a prediction must be reconstructed, the graph should identify the relevant
versions without retaining prohibited personal content. This is where ADLC
becomes architecture: the system must make evidence possible through interfaces,
metadata, and storage boundaries rather than asking an exhausted operator to
remember what happened.

## 05. Add agents, gateways, and protocol boundaries carefully

Agentic AI architecture extends a fixed workflow with a loop that can choose a
next step. A minimal loop has a goal, context, planner, tool selector, tool
gateway, observation, and stopping rule. The model proposes an action, but a
policy layer decides whether that action is permitted. A budget limits tokens,
time, tool calls, and spend. A trace records the plan and typed tool outcomes so
that a human can inspect a failure.

MCP and A2A are **advanced extensions** in this chapter. MCP-style tool or
context gateways expose capabilities through a protocol boundary; A2A-style
agent communication makes an agent’s capability discoverable to another agent.
The names do not remove the need for authentication, authorization, schema
validation, replay protection, and audit. Treat every remote tool as hostile to
the agent’s assumptions. A tool description is not a permission grant, and a
model-generated argument is not a trusted identity assertion.

For the running case, an agent may gather approved metadata and draft a routing
explanation. It may not retrieve arbitrary tenant documents, change retention,
or send a customer-facing message without a separately authorized action. The
gateway enforces an allow-list, validates JSON arguments, applies a deadline,
redacts sensitive results, and records tool name, policy decision, and outcome.
The agent receives a typed error when a tool is denied; it should not “try a
similar” privileged operation.

The main new failure mode is not only an incorrect answer. It is an incorrect
action sequence: prompt injection in retrieved content, tool confusion, loops,
data exfiltration, or an action that is individually valid but wrong in context.
Use retrieval boundaries, content provenance, least privilege, sandboxing,
human approval for high-impact actions, and deterministic validators around
side effects. Evaluate an agent on task success, constraint violations,
abstention, tool-call efficiency, and trace quality—not on fluent prose alone.

## 06. Derive scale and performance from a workload

Performance work starts with a workload declaration: request or event rate,
payload size, concurrency, model variant, dependency mix, and percentile target.
For a service that processes requests serially on one worker with mean service
time $s$, a first-order service rate is $\mu=1/s$. If arrivals average
$\lambda$, utilisation is $\rho=\lambda/\mu$. This approximation helps explain
why a service near saturation becomes sensitive to variability; it is not a
capacity guarantee for a distributed system.

For an M/M/1 queue under its assumptions, the expected time in system is

$$
W=\frac{1}{\mu-\lambda},\qquad \lambda<\mu.
$$

If $s=40\,\mathrm{ms}$, then $\mu=25$ requests per second. At $\lambda=15$,
$W=100\,\mathrm{ms}$ in the simplified model; at $\lambda=22.5$,
$W=400\,\mathrm{ms}$. The nonlinear increase is a reason to use bounded
queues, admission control, batching where safe, and autoscaling before the
service reaches a cliff. Actual tail latency also includes model warm-up,
garbage collection, network variance, storage, and correlated retries.

End-to-end latency can be decomposed as

$$
L=L_{queue}+L_{validation}+L_{features}+L_{model}+L_{policy}+L_{response}.
$$

Measure each term where possible. Optimizing a model by 10 ms is irrelevant if
a remote feature call contributes 300 ms and fails 2% of the time. Performance
optimization can include smaller models, quantization, caching, batching,
parallel independent reads, precomputation, efficient serialization, and
hardware selection. Each changes accuracy, freshness, cost, or failure modes;
record the trade-off in an architecture decision record.

Scale the right boundary. Stateless HTTP workers can often scale horizontally;
GPU memory, a serial feature store, or a human review queue may be the actual
bottleneck. Partition tenants or events only when ordering and fairness remain
defined. Backpressure protects downstream systems, but it also requires a user
experience for delayed, rejected, or degraded work. A “successful” 202 response
without durable ownership of the job is not resilience.

## 07. Design resiliency as controlled degradation

Resiliency is the ability to preserve an acceptable outcome when components,
networks, data, or assumptions fail. List failure modes before selecting a
pattern: unavailable model artefact, stale feature, overloaded queue, expired
credential, incompatible schema, dependency timeout, poisoned input, partial
rollout, and incorrect human override. For each, state detection, containment,
fallback, recovery, and evidence.

Timeouts bound waiting; retries can amplify load. Retry only an operation that
is safe to repeat or carries an idempotency key, use exponential backoff with
jitter, and cap attempts. Circuit breakers can stop calls to a failing
dependency, but an open circuit needs a meaningful fallback: cached metadata,
manual review, a lower-risk model, or explicit refusal. Bulkheads isolate a
noisy tenant or expensive model from unrelated work. A queue absorbs bursts but
does not make an unavailable downstream system healthy.

For AI, graceful degradation must preserve uncertainty. If a feature is stale,
the system may abstain rather than fabricate a confident score. If a model is
unavailable, a human queue may be safer than a silently substituted model. If a
retrieval index is incomplete, the answer should expose the limitation. Define
the fallback in product terms, not only in HTTP status codes.

Availability is a system property. If two independent sequential services have
availabilities $A_1$ and $A_2$, a simple approximation is

$$
A_{total}\approx A_1A_2.
$$

At $A_1=A_2=0.99$, the path is about $0.9801$, before shared network,
credentials, storage, and operator dependencies. Parallel redundancy changes
the equation but adds consistency and cost. Use the arithmetic to find hidden
coupling, then validate assumptions with failure injection and incident data.

## 08. Integrate infrastructure without hiding the system

Infrastructure integration translates responsibilities into executable controls.
Package a reproducible image or environment; pin dependencies and model artefact
identifiers; separate configuration from code; store secrets in an approved
secret manager; define network and identity policies; and make health, readiness,
shutdown, and resource limits observable. Containers and Kubernetes are
**supplementary/advanced extensions**, not a substitute for these principles.

An infrastructure blueprint should show compute, storage, queues, gateways,
observability, deployment controller, and trust zones. It should state which
data may cross each zone and which operator can change it. Infrastructure as
code makes a desired state reviewable, but a declarative file can still grant
excessive permission or create a costly topology. Include cost, quota, region,
backup, deletion, and disaster-recovery assumptions in the review.

Production readiness includes operational ownership. Define an SLO and error
budget, dashboards that distinguish traffic from errors, alerts with runbooks,
on-call escalation, release stages, rollback, migration compatibility, and a
post-incident learning path. OpenTelemetry is a **supplementary** observability
option; whichever tooling is used, trace identifiers should cross gateway,
model, tool, and policy boundaries without storing raw sensitive content.

The architecture should make a safe change small. A canary or shadow release
compares a candidate against a stable version on an approved slice. A rollback
must restore model, policy, and infrastructure compatibility, not only the
container tag. A data schema migration should support old and new readers long
enough to drain in-flight work. “Deploy succeeded” is not evidence that the
decision quality or safety constraints remained acceptable.

## 09. Govern the whole decision and run the study lab

Governance is not a final approval stamp. It is the set of rules, evidence,
roles, and recourse that make an AI system accountable over time. Establish a
system card: purpose, users, non-users, data categories, model and policy
versions, evaluation slices, known limitations, prohibited uses, human review,
security controls, retention, and contact owners. Add an architecture decision
record for every consequential trade-off, including alternatives rejected and
assumptions that must be revisited.

Security and privacy are part of correctness. Threat-model prompt injection,
training-data leakage, model extraction, tenant crossover, supply-chain
compromise, denial of service, and operator misuse. Minimize collected data,
redact logs, enforce tenant isolation, rotate credentials, validate dependencies,
and test deletion and access requests. A governance control that cannot be
tested is a hope. A metric that hides a subgroup or domain failure is not a
complete evaluation.

The practical lab is to build a deterministic architecture manifest checker.
Give it components, trust zones, dependencies, data classes, SLOs, and fallback
policies. It should reject a missing owner, unbounded dependency timeout,
unversioned model, privileged tool without an approval rule, and an SLO without
a percentile. Then write a failure matrix for a stale feature, overloaded
queue, model download failure, and denied tool call. Record the manifest hash,
test output, and an explanation of what the checker cannot prove.

The six project contracts below turn the chapter into a progression. Start with
the manifest and a modular design, then compare service and event styles, add an
agent gateway, measure a workload, inject failures, and finally reproduce a
published systems claim. Every project must retain licences, versions,
assumptions, and negative results. A benchmark is evidence for a declared
workload, not a universal ranking.

## 10. Oral questions, summary, and references

Ask yourself: Which responsibility belongs at the model boundary and which at
the policy boundary? When is a modular monolith safer than microservices? What
does ADLC preserve that a training script does not? Why should an agent gateway
be treated as an authorization boundary? Which term dominates the latency
budget? What fallback preserves a safe outcome when a feature is stale? What
evidence would let an affected person challenge a decision? Which infrastructure
assumption is shared by otherwise “independent” services?

The central lesson is simple but demanding: architect the decision path, not
only the model. Name components and owners; make contracts, versions, trust
zones, and failure modes explicit; choose an architectural style by workload
and change risk; use ADLC to carry evidence from framing through retirement;
constrain agents and gateways; derive scale and performance from measurements;
design degradation that preserves uncertainty; integrate infrastructure as
reviewable controls; and govern the system as a socio-technical product. The
next chapter should make these boundaries concrete with a component catalogue,
compatibility matrix, and architecture decision record.

### Python implementation: a bounded architecture manifest validator

This first-principles example uses Python 3.12+ and only the standard library.
It validates structural invariants; it does not prove that a design is secure,
available, fair, or fit for a real domain. Complexity is $O(C+D)$ for $C$
components and $D$ declared dependencies, with $O(C+D)$ memory. Run it with
`python manifest_validator.py` after replacing the sample dictionary, or paste
the function into a typed test module.

```python
from __future__ import annotations

from typing import Any, Mapping


class ArchitectureError(ValueError):
    """Raised when a manifest violates a reviewable architecture invariant."""


def validate_manifest(manifest: Mapping[str, Any]) -> list[str]:
    """Return deterministic errors for a small, bounded AI architecture manifest."""
    if not isinstance(manifest, Mapping):
        raise TypeError("manifest must be a mapping")
    components = manifest.get("components")
    if not isinstance(components, list) or not components:
        raise ArchitectureError("components must be a non-empty list")

    errors: list[str] = []
    names: set[str] = set()
    for component in components:
        if not isinstance(component, Mapping):
            errors.append("each component must be an object")
            continue
        name = component.get("name")
        if not isinstance(name, str) or not name.strip():
            errors.append("component name is required")
            continue
        if name in names:
            errors.append(f"duplicate component: {name}")
        names.add(name)
        for field in ("owner", "version", "trust_zone"):
            if not isinstance(component.get(field), str) or not component[field].strip():
                errors.append(f"{name}: {field} is required")
        timeout = component.get("timeout_ms")
        if not isinstance(timeout, (int, float)) or timeout <= 0:
            errors.append(f"{name}: timeout_ms must be positive")
        if component.get("side_effects") and not component.get("approval_rule"):
            errors.append(f"{name}: side effects require approval_rule")

    for dependency in manifest.get("dependencies", []):
        if not isinstance(dependency, Mapping):
            errors.append("dependency must be an object")
            continue
        source, target = dependency.get("source"), dependency.get("target")
        if source not in names or target not in names:
            errors.append("dependency references an unknown component")
    slo = manifest.get("slo")
    if not isinstance(slo, Mapping) or slo.get("percentile") not in {"p95", "p99"}:
        errors.append("slo.percentile must be p95 or p99")
    fallback = manifest.get("fallback")
    if not isinstance(fallback, str) or not fallback.strip():
        errors.append("fallback policy is required")
    return errors


if __name__ == "__main__":
    sample = {
        "components": [{"name": "model", "owner": "ml", "version": "v1",
                        "trust_zone": "private", "timeout_ms": 200}],
        "dependencies": [], "slo": {"percentile": "p95"},
        "fallback": "human-review",
    }
    print(validate_manifest(sample))
```

Expected output is `[]` for the sample. Add tests for duplicate names, unknown
dependencies, missing approval rules, non-positive timeouts, and a malformed
manifest. The validator catches omissions in a document; it cannot inspect a
cloud account, verify a model’s accuracy, or replace a human architecture and
governance review.

### Practical assignment and quiz

1. Produce an architecture decision record comparing a modular monolith and an
   event-driven design for the running case. Include owners, data boundaries,
   latency, cost, failure modes, and rollback.
2. Extend the validator with a bounded retry policy and a check that every
   side-effecting component has an idempotency key.
3. Measure a local workload’s p50, p95, and p99 latency; explain why the mean
   cannot stand in for the tail.
4. Threat-model a tool gateway that can read documents but cannot delete them.
5. Quiz: distinguish readiness from liveness; state one reason retries amplify
   failure; name two agent safety controls; derive $\rho=\lambda/\mu$; explain
   why model, policy, and infrastructure versions must roll back together.

**Answer guidance:** A strong answer names a boundary, an observable signal, an
owner, and a failure or governance consequence. It distinguishes an educational
approximation from a production claim, labels supplementary tools, and cites
the source or experiment that supports a factual statement.
